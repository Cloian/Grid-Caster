# Grid-Caster 개발 워크플로우

## 기준과 상태

2026-10-02 확정한 [게임 정체성](game-identity-2026-10-02.md)을 실제 플레이로 검증하고 완성하는 순서다. 정체성·용어 정리는 완료했다. 1단계의 PC 화면 분리·공통 배치 구현은 진행했으며 [검증 기록](../verification/pc-screen-baseline-2026-10-02.md)과 별도로 사람의 판독성 확인이 남아 있다. 2단계에서는 [첫 스테이지 규칙 감사](../verification/stage-one-audit-2026-10-02.md)로 불길 제거·클리어 후 입력 재개·시간 표시 불일치를 수정하고 빌드별 회귀 검사·로컬 플레이 기록 도구·[사람 플레이 프로토콜](stage-one-playtest-protocol-2026-10-02.md)을 준비했다. **2단계의 재미 검증은 아직 완료하지 않았다.** 클리어 결과/같은 씬 재시작은 정리했지만 3단계의 보스·30분 흐름과 4단계 이후는 앞으로 할 일이다. 현재 코드나 과거 검사 통과를 미래 단계 완료로 표시하지 않는다.

한 번에 한 단계의 작은 작업만 수행한다. 완료 조건이 충족되지 않으면 그 단계에서 수정·축소·재검증하며, 새 콘텐츠로 문제를 덮지 않는다. 워크플로우 최초 작성은 문서만 변경했고, 이후 PC 화면 작업에서 코드와 로컬 검증 빌드를 변경했다. 저장 씬·공개 배포는 변경하지 않았다.

## 1. PC 보드 경험과 입력 기준 정리 — Supporting

**목표:** 플레이어가 전장 전체를 읽을 수 있는 PC 화면을 기준점으로 만든다.

- 네이티브 PC와 Web의 화면 분기를 확인한다. 데스크톱 Web은 PC UI, 모바일 브라우저는 기존 터치 UI로 분리했다. 공개 배포 갱신은 별도 작업이다.
- 13×13 내부 칸과 외벽, 플레이어·적·공격선·위험 칸을 한 화면에 유지한다. 카메라 추적·줌을 되살리지 않는다.
- 강화·유물은 보드 밖, 웨이브·시간은 윗벽 근처, 체력·준비도·조작은 아랫벽 근처로 정리한다. 창 크기를 바꿔도 보드를 가리거나 과도한 공백이 생기지 않게 확인한다.
- A 일반 공격 / S 기본 이동·이동술 / F 준비한 특성 공격과 마우스 미리보기·확정을 짧게 안내한다. 목록·설명·선택창을 닫는 입력이 전투에 전달되지 않게 한다.

관련 범위: `MobilePlaytestController`, `GameHudController`, `CameraController`, `DirectionalActionIndicator`, 기존 Web 빌드 도구. 새로운 UI 체계를 통째로 만들지 않는다.

**검증·완료 조건:** 지원할 작은 창·큰 창·가로세로 비율을 기록하고 각 화면에서 모든 칸과 상시 HUD가 겹치지 않음을 확인한다. 키보드·마우스, 추가 시전 중 이동 차단, 무료 이동, 목록 입력 차단과 모바일 회귀를 검사한다. 사람 플레이에서도 타일·위험·준비 상태를 구분할 수 있어야 한다. 자동 검사만 통과하면 화면 경험 검증 완료가 아니다.

## 2. 첫 스테이지의 판단·빌드 재미 검증 — Core

**목표:** ‘도망치고 쏘기’ 외에 준비와 배치로 더 좋은 결과를 만드는 선택이 생기는지 확인한다.

- 현재 네 시작 특성과 공통 이동술·강화·유물을 비교 기준으로 고정한다. 현재 다른 특성 전용 보상은 제외되어 있으므로 무제한 교차 빌드를 먼저 열지 않는다.
- 동일한 적 배치·성장 조건에서 재조준, 직선 다수 대상, 직접 처치·초과 피해, 변위·충돌이 서로 다른 판단을 만드는지 비교한다.
- 나이트·비숍·룩의 위협이 정보대로 작동하는지, 이동술이 공격 준비와 탈출 사이에서 선택을 만드는지 관찰한다. 플레이어 행동 후 적 한 번이라는 턴 순서를 유지한다.
- 필요할 때 위협·배치·보상 조건 중 한 변수만 바꾼다. 피해·물량 증가만으로 사고의 깊이를 만들었다고 평가하지 않는다.
- 보상 요약은 핵심 효과와 조건, 상세는 정확한 범위·현재/선택 후 단계로 구분한다. 규칙 설명과 실제 결과가 어긋나는 버그를 먼저 고친다.

관련 범위: `PlayerTraitSystem`, `RunProgressionSystem`, `RunProgressionCatalog`, 설명/UI, `Move`, `ChessMonsterBehaviour`, 위협 예고와 기존 전술 검증 도구. 수정 파일은 실제 관찰 후 최소 범위로 정한다.

**플레이 기록:** 선택 빌드, 주요 보상, 이동/일반/특성 공격 횟수, 준비한 공격의 사용 상황, 반복 도주 구간, 사망 원인, 사용자가 설명한 좋은 한 수를 남긴다. 설명을 먼저 주입하지 않고 무엇을 이해했는지 관찰한다.

기록 방법과 네 빌드의 비교 질문은 [첫 스테이지 플레이 프로토콜](stage-one-playtest-protocol-2026-10-02.md)을 따른다. `Tools > Playtest > Record Local Play Sessions`는 기본 꺼짐인 Editor 전용 로컬 관찰 도구이며 의도·재미·사망 원인을 추측하지 않는다. 자동 픽스처와 사람 플레이를 같은 결과로 집계하지 않는다. 요청에 따라 기존 Unity 앱에서 검증하며 새 웹 링크·서버·테스트 프로젝트를 만들지 않는다.

**완료 조건:** 각 빌드에서 플레이어가 위치·순서를 고른 이유와 그 선택의 큰 결과를 설명할 수 있고, 반복 도주만이 유효한 해법인 구간이 줄어야 한다. 턴·경로·점유·추가 시전·불길·보상 회귀도 통과해야 한다. 재미가 약하면 중복 효과를 덜어내거나 조건을 조정하고 이 단계를 반복한다.

## 3. 첫 스테이지 보스와 약 30분 흐름 완성 — Core

**목표:** 학습 → 압박 → 빌드 실현 → 보스 검증으로 끝나는 한 런을 만든다.

- 현재 고정 20웨이브를 기준선으로 사용한다. 10·20웨이브의 혼합전은 고유 보스가 아니라 임시 만남이다.
- 먼저 기존 이동·사선·특성 공격으로 풀 수 있는 스테이지 보스의 역할과 전조를 설계하고, 한 패턴의 그레이박스부터 검증한다. 상세 패턴·수치·새 규칙은 해당 작업에서 결정한다.
- 보스가 빌드와 이동술을 무효화하는 임의 면역이나 기존 턴 규칙을 깨는 공격으로 어려움을 만들지 않게 검토한다.
- 웨이브별 학습, 특수 몬스터 해금, 유물 위험·보상, 회복, 보스 진입 시 성장량과 체력을 함께 조절한다.
- 클리어 안내와 같은 스테이지 새 런 재도전은 기존 결과 패널로 구현했고, 네 시작 특성의 종료/재시작 회귀를 확인했다. 이는 고유 보스·30분 흐름 검증 완료가 아니다. 종료 후 메뉴로 입력이 다시 열리지 않음을 계속 유지한다.

관련 범위: `WaveTemplate`, `MonsterSpawner`, `StageFlowManager`, 보스에 필요한 최소 행동 코드, `GameHudController`, 보상 흐름. 전용 보스는 이 단계에서만 범위를 확정해 추가한다.

**검증·완료 조건:** 여러 빌드의 실제 사람 플레이로 보스 포함 길이, 고민·보상 선택 시간, 죽는 구간, 쉬운 반복 구간을 기록한다. 약 30분은 목표이며 강제 대기나 제한 시간을 추가하지 않는다. 자동 강제 처치·배속 시뮬레이션은 길이 측정에 쓰지 않는다. 웨이브 수 변경이 필요하면 근거를 제시해 결정한다. 보스 승패의 원인을 읽고 재도전할 수 있으며 클리어 후 입력·성장 상태가 정상 정리돼야 한다.

## 4. 스테이지 경계·기록·중단 대응 정리 — Supporting

**목표:** 새 스테이지와 재도전에서 새 빌드가 보장되고, 이미 달성한 기록은 잃지 않는다.

- 스테이지 식별과 최소 선택/전환 흐름을 만들고 런 상태와 클리어 기록을 분리한다. 장대한 탐험·스토리·영구 성장 체계는 만들지 않는다.
- 새 런에서 시작 특성·강화·유물·이동술·특성 충전·무료 이동·잔류 위험·점유·웨이브 상태를 초기화한다.
- 현재 스테이지 사망은 그 스테이지 재도전으로, 클리어는 기록 저장과 다음 독립 런으로 연결한다. 이전 기록은 새 런 사망으로 삭제하지 않는다.
- 약 30분 플레이의 중단에 대비해 저장 대상·안전한 저장 시점·사망/클리어 시 처리·버전 변경 시 복원을 먼저 정한다. 중단 저장은 클리어 기록 및 영구 성장과 별개다. 현재 복원 기능은 없으며 클라우드/계정/외부 서비스 도입은 승인하지 않는다.

관련 범위: `StageFlowManager`, 게임 시작/재시작 흐름, 성장·턴 상태 소유 클래스, 최소 기록 저장과 UI. 중단 저장의 상세 범위는 구현 전 별도 결정한다.

**검증·완료 조건:** 다른 스테이지 진입·현재 스테이지 사망·클리어·재실행 각각에서 성장 잔존/누락, 이벤트 중복, 점유 잔존, 기록 손실이 없어야 한다. 재실행 후에도 클리어 기록을 확인한다. 중단 복원을 제공한다면 완료된 턴 상태로 재개하며, 제공하지 않는 범위는 사용자에게 명확히 알린다.

## 5. 후속 스테이지와 제한된 속성 실험 — Core 확장

**진입 조건:** 첫 스테이지가 2·3단계의 경험 검증을 통과하고 독립 런 경계가 안정적이어야 한다.

- 우선 2스테이지 하나에서 달라지는 공간 문제를 정의한다. 배경·적 수만 바꾸지 않는다. 맵 크기·기믹·보상 풀은 이 작업의 설계 대상이다.
- 공통 보상 원리를 유지하면서 스테이지 전용 시작 후보와 보상 풀을 소규모로 추가한다. 시작 핵심 하나 → 성장 조합의 구조를 유지한다.
- 번개·얼음·화염·바람 중 필요한 후보를 소수만 그레이박스로 시험한다. 네 속성 전체, 반응표, 저항표를 한꺼번에 만들지 않는다.
- ‘이 속성 때문에 어떤 위치·표적·행동 순서를 달리 골랐는가’를 기존 네 특성과 비교한다. 이름만 다른 효과는 통합·대체·보류한다.
- 조합별 시전·봉쇄·연쇄 상한과 보스 대응을 검증한다. 2스테이지 검증 전 3스테이지 전체 제작으로 확장하지 않는다.

**완료 조건:** 새 맵에서 배운 규칙과 성장 선택이 서로 연결되고, 이전 스테이지의 완성 빌드를 가져오지 않아도 새로운 해법을 쌓는 재미가 있어야 한다. 새 특성의 판단 차이를 플레이어가 설명할 수 있어야 하며 기존 전투 회귀를 유지한다.

## 6. 피드백·아트·배포 정리, 모바일 재평가 — Polish / Later

- 핵심 검증을 통과한 효과에만 가독성·애니메이션·VFX·사운드를 보강한다. 기존 스타일 문서와 확정된 기준 리소스를 따르며 32 PPU·Point·독립 몬스터 애니메이션 원칙을 유지한다.
- PC 배포는 웹 링크/다운로드 중 테스트 목적에 맞게 따로 결정한다. 공개 게시·새 빌드 배포는 해당 요청 범위에서 진행한다.
- 모바일은 보조 실험으로 다시 평가한다. 동일 전투에서 전체 보드 읽기와 방향 선택이 전달되는지 확인하고, 모바일 편의 때문에 PC 핵심을 바꾸지 않는다.
- PC 화면, 전투, 웨이브·성장, 보스, 런 초기화·기록의 검증 자료와 알려진 한계를 버전별로 남긴다.

**완료 조건:** 연출이 정보를 가리지 않고, 배포 빌드에서도 동일 규칙과 기록이 유지된다. 모바일 검증이 만족스럽지 않으면 PC 주력을 유지하고 모바일 확대는 보류한다.

## 매 작업의 반복 절차

1. 요청 범위와 관련 코드·씬·설정·기존 변경을 확인한다.
2. 가설을 한 문장으로 적고 성공을 관찰할 방법을 정한다.
3. 변경 파일·현재 동작·변경할 동작을 정리하고 실행 가능한 최소 단위로 구현한다.
4. 자동 검사로 입력·턴·경로·점유·피해·보상·초기화의 규칙 일치를 확인한다.
5. 경험 변경은 사람 플레이로 확인한다. 실행하지 않은 검증은 미실행으로 표시한다.
6. 유지 / 조정 / 통합 / 제거 / 보류를 근거와 함께 선택한다. 큰 정체성 변경은 먼저 사용자에게 묻는다.
7. 구현 상태와 기획·설명·검증 기록을 맞춘다. 커밋·브랜치·게시가 요청된 경우 [CONTRIBUTING.md](../../CONTRIBUTING.md)를 따르고 이번 작업과 무관한 변경은 포함하지 않는다.

**바로 다음 작업:** 기존 Unity의 `SampleScene`에서 PC 판독성과 네 빌드의 판단 차이를 사람 플레이로 관찰한다. 준비된 규칙 감사와 기록 도구를 재사용하고, 반복 도주 구간과 좋은 한 수를 연결해 한 변수씩 조정한다. 사람이 설명한 판단·쾌감의 근거 없이 새 보스·속성·후속 맵으로 검증 단계를 건너뛰지 않는다.
