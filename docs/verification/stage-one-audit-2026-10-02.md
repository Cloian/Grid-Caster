# 첫 스테이지 전술·빌드 점검

## 범위

PC 화면 정리 다음의 2단계 작업이다. 원본 Grid-Caster 프로젝트의 기존 Unity 6000.4.0f1 창에서 실행했다. 웹 빌드·서버·새 링크·새 검증 프로젝트는 만들지 않았다. 씬·Prefab·기존 아트·패키지·렌더 설정과 적 능력치·웨이브 수는 변경하지 않았다.

자동 검사는 규칙 일치와 진행을 확인한다. 사람의 선택 이유·재미·약 30분 길이는 확인하지 않았다. 새 보스·속성·후속 스테이지는 이번 범위에 포함하지 않는다.

## 재현해 수정한 게임 버그

일반 공격이 불길 위의 적에게 적중하면 앞쪽 빈 바닥의 불길만 없어지고 적중 칸의 불길은 남았다. `TurnProjectile.FindImpact`가 몬스터를 찾자마자 종료하면서 바닥 콜백을 생략한 것이 원인이다.

바닥 여부를 먼저 확인해 적이 서 있는 칸에도 경로 콜백을 적용한다. 외벽은 여전히 제외한다. 첫 적 뒤는 일반 공격으로 지워지지 않으며, 준비된 관통만 유효 적중 뒤 경로를 이어간다. 미리보기는 콜백을 전달하지 않아 불길·점유·RNG를 바꾸지 않는다.

- [수정 전 재현](stage-one-tactical-20261002-220604.txt): 적중 바닥의 불길 제거 조건 실패.
- [수정 후 전술 검사](stage-one-tactical-20261002-221103.txt): 67조건 통과.
- [기록 도구 포함 검사](stage-one-tactical-20261002-221600.txt): 69조건 통과. 두 추가 조건은 일반/관통 특수공격을 행동 단위로 관찰하는 검사다.

## 확장한 통제 사례

- 기존 45조건의 충전·취소·소모·무료 이동·추가 방향 선택·벽 제외 경로를 유지.
- 적중 칸과 빈 경로의 불길 제거, 첫 적 뒤 불길 보존, 관통 두 대상까지 정화.
- 삼중 재조준에서 세 대상 처리·원래 발사 위치 보존·이동 차단·대기 중 적 턴 정지·적 턴 한 번.
- 직접 처치의 초과 피해 한도·인접 대상 한 명·비연쇄 처리.
- 실제 넉백 충돌 피해, 직접 대상 2행동/첫 충돌 상대 1행동 봉쇄, 주변 적 제외.
- 관통 두 명 직접 적중의 회복이 웨이브당 두 번에서 멈춤.
- 나이트 Lv.2 착지 불길 제거가 진입 피해보다 먼저 적용.
- 룩 상단 외벽 장전·고정 열 피해 2·재정비 한 행동.

## 클리어 후 입력 재개 버그와 결과 안내

[수정 전 재현](stage-end-20261002-224440.txt)에서 `StageCleared`로 입력을 잠근 뒤 일시정지/계속 API를 호출하면 살아 있는 플레이어의 입력이 다시 열렸다. `GameHudController`의 일시정지 해제 조건이 사망만 확인하고 클리어를 확인하지 않은 것이 원인이다. 클리어 뒤 플레이 시간이 계속 증가하는 문제도 같은 종료 조건 누락이었다.

사망을 뜻하는 `IsGameOver`는 유지하고, 별도 `IsStageCleared`와 통합 `IsRunEnded`로 메뉴·입력 복원·시간 진행을 차단한다. 오래된 시작 카드 콜백도 종료된 빌드를 바꾸지 않는다. 보조 모바일의 메뉴/백그라운드 처리도 이 상태를 따른다.

UI 스킬에 따라 새 화면 체계를 추가하지 않고 기존 결과 패널을 재사용했다. 클리어 시 ‘스테이지 클리어 / WAVE 20 / 플레이 시간 / 새 빌드 시작’을 표시한다. ESC는 패널만 숨기고 전투와 시간을 계속 정지한다. 같은 씬의 실제 재로드로 새 특성·강화·유물·이동술·충전·웨이브·체력·묘비를 초기화한다. 기록 저장·다음 스테이지·고유 보스·엔딩은 만들지 않았다.

[최종 종료 회귀](stage-end-20261002-225451.txt)는 네 시작 특성에서 72조건을 통과했다. 최종 웨이브 스폰 API를 사용하되 성장/웨이브/처치는 압축한 fixture다. 정상 20웨이브 완주가 아니다. 실제 `GraphicRaycaster`가 재시작 버튼을 받는지, 문구가 기존 픽셀 폰트 영역에 들어가는지, 결과 오버레이가 보드 밖 성장 패널도 차단하는지 확인했다.

[최종 캡처](captures/stage-clear-20261002-225449.png)를 직접 확인했다. 최초 캡처의 밝은 배경은 시각 검증에서 발견해 원래 어두운 패널을 보존하고 외곽선만 강조하도록 수정했다. [중간 60조건 통과](stage-end-20261002-225102.txt)는 기능 검사만 통과한 자료이며 최종 시각 결과가 아니다.

## 시간 표시 공통화와 보조 입력

[실제 상세창 재현](mobile-adapter-20261002-230850.txt)에서는 PC HUD의 시간은 멈췄지만 모바일의 별도 시간은 계속 증가했다. 결과 패널은 PC HUD 시간을 사용해 화면과 종료 시간이 달라질 수 있었다. 터치 HUD가 `GameHudController.ElapsedPlayTime`을 읽도록 통합했다. 새로운 게임 시간/턴 시스템은 추가하지 않았다.

[첫 타이머 fixture 실패](mobile-adapter-20261002-230621.txt)는 미보유 강화의 상세창을 요청해 창이 열리지 않았던 검사 구성 오류이며 타이머 버그 재현 증거가 아니다. 해당 강화를 보유한 상태에서 상세창을 실제로 열고 1.2초를 관찰한 이후 재현과 구분해 보존했다.

[최종 보조 입력 회귀](mobile-adapter-20261002-231157.txt)는 35조건 통과다. 미리보기/실행·추가 시전 재조준과 이동 차단·상세창 공통 시간·클리어 전장 확인 버튼·메뉴로 결과 복귀·백그라운드에서 종료 상태 유지가 포함된다. Unity의 강제 모바일 어댑터/통제 fixture와 세로 배치 계산이며 실제 아이폰·Safari 실행은 아니다. 웹 빌드나 링크를 새로 만들지 않았다.

## 정상 능력치 자동 런

[8런 원본](stage-one-smoke-20261002-221703.json)은 시작 체력 10, 기본 피해 1, 기존 성장·턴·웨이브를 사용했다. 연출만 배속했으므로 체감 플레이 시간 자료가 아니다. 기존 `heuristic-v5-manual` 봇 정책이며 미래 RNG를 읽거나 체력을 강제로 채우지 않는다. 효과 검사 228조건도 통과했다.

클리어 UI/종료 차단 수정 뒤 [최종 정상 8런](stage-one-smoke-20261002-225549.json)을 다시 실행했다. 효과 228조건·8런 완료·게임 오류 0이며 종료 유형과 행동 수는 아래 최초 기록과 같았다. 반복 실행을 별도 시드의 독립 표본 16런으로 합산하지 않는다.

| 빌드 | 시드 2400 | 시드 2401 |
| --- | --- | --- |
| 더블 캐스트 | 20웨이브 클리어, 580입력 선택 | 클리어, 817입력 선택 |
| 관통 | 7웨이브 클리어 후 사망, 160선택 | 동일 종료, 160선택 |
| 데미지 강화 | 16웨이브 클리어 후 17웨이브 턴 상한, 594선택 | 클리어, 553선택 |
| 넉백 | 15웨이브 클리어 후 사망, 406선택 | 19웨이브 클리어 후 사망, 600선택 |

더블 캐스트의 추가 방향 선택도 ‘입력 선택’에 포함돼 선택 횟수와 세계 턴 수는 다르다. 검사 코드의 완료/PASS는 8런을 오류 없이 실행했다는 뜻이며 모든 런이 승리했다는 뜻이 아니다. 표본 2시드/빌드로 난이도나 빌드 우열을 일반화하지 않는다.

17웨이브 턴 상한에서는 체력 1인 비숍 한 마리를 남겨 둔 채 비숍 이동술을 반복했다. 적과 플레이어는 계속 움직이므로 입력/턴 정지가 아니다. 기본 한 칸 이동도 가능한 공개 보드에서 봇 정책이 안전한 대각 이동을 반복한 사례다. 기존 ‘비숍 색 전환’ 진단 옵션으로 별도 정책을 비교하되 결과를 기본 정책 승률과 합산하지 않는다. 이를 이유로 적 AI·피해·이동술 규칙은 바꾸지 않았다.

[별도 비숍 정책 진단](stage-one-bishop-policy-20261002-223648.json)은 같은 전투 소스 해시에서 8런을 실행했다. 마지막 적이 비숍이고 서로 다른 칸 색이면 색을 바꾸는 기본 이동을 더 높게 평가하는 **봇의 선택 정책만** 켰다. 데미지 강화/시드 2400은 510선택·20웨이브 클리어·체력 6으로 끝났고, 나머지 일곱 런의 종료와 행동 수는 기본 정책 기록과 같았다. 진단 정책에서는 턴 상한 종료가 없었다.

이는 이 반복 사례에 진행 가능한 선택이 있었다는 증거다. 인간에게도 그 선택이 읽히는지, 재미있는지는 증명하지 않는다. 동일 초기 시드라도 이후 행동·RNG 소비·보드가 달라지므로 같은 전장에 두 변수를 짝지은 밸런스 실험으로 해석하지 않는다. 이 진단에는 효과 228조건을 다시 실행하지 않았다.

### 별도 시드의 확장 점검

기존 `Validate Run Balance` 메뉴로 시드 1000~1007을 각 빌드에 적용한 [추가 32런](stage-one-expanded-20261002-232623.json)을 완료했다. 기본 정책·체력 10·피해 1·같은 전투 소스 해시를 사용했고 게임 예외·Editor 진단은 0이다. 이 메뉴는 효과 228조건을 다시 실행하지 않았다. 메뉴의 기본 출력 이름은 실행 후 시각별 이름으로 보존했다.

| 빌드 | 클리어 | 사망 | 봇의 웨이브별 입력 상한 |
| --- | --- | --- | --- |
| 더블 캐스트 | 0 | 7 | 1: 시드 1002, 14웨이브 |
| 관통 | 3 | 4 | 1: 시드 1006, 13웨이브 |
| 데미지 강화 | 2 | 5 | 1: 시드 1007, 16웨이브 |
| 넉백 | 1 | 7 | 0 |

합계 6클리어·23사망·3상한이다. 앞선 시드 2400~2401에서는 더블 캐스트 두 런이 클리어하고 관통 두 런이 초반에 사망했지만, 새 시드에서는 반대 양상이 나왔다. 초기 표본만으로 ‘관통은 불가능 / 더블 캐스트는 우월’이라고 결론 내리지 않는다. 이 정책은 고정 보상 선호와 단기 위치 평가를 사용하므로 사람의 숙련도·빌드별 최적 전략을 대표하지 않는다.

추가 세 상한 사례는 런이 중단된 자동 정책 자료다. 이 메뉴는 첫 시드의 초기 24선택만 상세 기록하므로 세 사례의 마지막 보드를 이 파일로 재구성할 수 없다. 기존 17웨이브의 비숍 색 반복과 동일 원인이라고 단정하거나 미해결 게임 버그로 표시하지 않는다. 다음 사람 테스트에서는 남은 적 수·이동술·기본 이동 대안·마지막 보드를 로컬 기록과 함께 확인한다.

## 로컬 플레이 기록 도구

신규 `Assets/Editor/PlaySessionRecorder.cs`는 기본 꺼짐, Editor 전용이다. 선택한 강화/유물, 일반·특수공격/기본 이동·이동술 횟수, 턴과 보드 상태를 새 JSON으로 기록한다. 게임 입력·난수·판정·제품 빌드·네트워크에는 관여하지 않는다.

[통제 검사 기록](play-sessions/session-20261002-221554-485.json)은 67이벤트, 일반 공격 9, 특수공격 13, 이동술 2, 세계 턴 24, 관찰 오류 0이다. 인간의 정상 런이 아니라 테스트 fixture 자료로 명시했다. 검사 후 기록 기능은 꺼 두었다. 상세한 사용법과 기록 한계는 [플레이테스트 절차](../design/stage-one-playtest-protocol-2026-10-02.md)를 따른다.

## 기존 전체 회귀 검사 정리

구형 카메라 검사에서 기존 가정과 현재 PC 구성의 차이가 발견됐다. [첫 실패 원본](stage-one-chess-before-camera-assert-20261002-221909.txt)을 보존했다. 카메라 Transform과 맵 중심의 일치 대신 화면상의 보드 영역 중앙을 검사하도록 수정했다.

[프레임 진단 기록](stage-one-chess-frame-diagnostic-20261002-222226.txt)도 보존했다. `EditorApplication.update`는 게임 프레임마다 한 번만 호출되는 것이 아니므로 기존 다른 검사기처럼 `Time.frameCount`별로 한 번 진행하도록 수정했다. **프레임 대기만으로 화면 비교 실패는 해결되지 않았다.**

[실제 픽셀 진단](stage-one-chess-pixel-diagnostic-20261002-222956.txt)에서 이 Editor의 검사 콜백 `Screen`은 1732×1384, 전체 화면 카메라의 실제 렌더는 1731×1337이었다. `CameraController`가 런타임에 캐시한 화면 크기는 실제 카메라 렌더와 일치했다. 검사기의 기대값만 런타임 크기를 사용하게 수정했다. 카메라가 전체 화면인지·캐시한 크기가 실제 렌더와 같은지도 별도 조건으로 검사해 잘못된 뷰포트를 숨기지 않는다. 이 차이를 모든 Unity 환경의 상시 동작으로 일반화하지 않는다.

[PC 실제 화면 회귀](pc-board-layout-native-20261002-223356.txt)는 공통 배치·보드 밖 HUD·8방향/이동 클릭 검사를 통과했다. 구형 HUD의 부모 기준 `anchoredPosition` 고정값도 실제 화면상의 순서·중앙·간격 검사로 교체했다. 상태 문구가 버튼 위로 분리된 현재 구성에서는 문구 위쪽을 기준으로 아랫벽 간격을 검사한다. 게임의 턴이나 카메라/HUD 배치를 검사 통과용으로 변경하지 않았다.

클리어 UI 추가 뒤 [PC 배치 재회귀](pc-board-layout-native-20261002-230140.txt) 31조건과 [전술 재회귀](stage-one-tactical-20261002-230210.txt) 67조건을 통과했다. 전술 검사 때 로컬 기록 기능은 꺼져 있어 기록 도구의 두 선택 조건은 다시 집계하지 않았다.

최종 [전체 체스 회귀](stage-one-chess-20261002-2236.txt)는 662조건을 통과했다. PC 실제 화면 검사는 31조건을 통과했다. 체스 회귀는 강한 체력/강제 처치가 포함된 통제 fixture이므로 정상 능력치 8런이나 인간의 클리어와 합산하지 않는다.

[보상 설명·선택 회귀](reward-usability-20261002-223756.txt)는 867조건을 통과했다. 현재/선택 후 이동술 단계, 최대 중첩 제외, 상세 문구 잘림, 실제 UI 레이캐스트와 위험 제단 등급 보장을 확인했다. 이는 조건 수이며 서로 독립된 867회 플레이가 아니다. 기본 메뉴의 PC/보상 보고서는 실행 시각별로 저장하도록 변경해 과거 결과를 덮어쓰지 않는다.

시간 표시 공통화 뒤 [최종 체스 전체 회귀](stage-one-chess-final-20261002-231522.txt) 662조건과 [최종 설명·선택 회귀](reward-usability-20261002-231242.txt) 867조건을 재실행해 통과했다. 서로 다른 종류의 검사 조건을 단일 승률·재미 점수로 더하지 않는다.

[마지막 PC 배치 회귀](pc-board-layout-native-20261002-231709.txt)도 31조건을 통과했다. 마지막 코드 상태에서 `git diff --check`를 통과했고, 저장 씬·Packages·ProjectSettings에는 변경이 없다.

## 원본 Unity 인계 상태

자동 검사 후 원본 `SampleScene`에서 실제 키보드 `1`로 특성을 선택하고, 다시 `1`로 시작 증강을 선택했다. `A`에서 8방향 화살표, `S`에서 주변 이동 가능 칸이 보였다. 충전 0 상태의 `F`는 특수공격을 실행하지 않았고 적 위치·체력은 그대로였다. 이는 키보드 선택과 초기 입력 확인이며, 충전된 특수공격·마우스 실행·정상 클리어를 직접 플레이한 증거는 아니다.

확인 후 Play를 종료하고 다시 시작해 **기존 Unity 창을 새 시작 특성 선택 화면**에 두었다. 추가 Inspector 설정 없이 카드 클릭 또는 숫자 1~4로 시작할 수 있다. 로컬 기록 기능은 꺼 두었다. 이 인계 과정에서 저장 씬을 수정하지 않았다.

## 변경 파일과 설정

- 런타임 수정: `TurnProjectile.cs`의 불길 콜백 순서, `GameHudController.cs`의 종료 상태·기존 결과 패널·공통 시계 읽기, `MobilePlaytestController.cs`의 공통 종료/시계 참조.
- Editor 신규: `PlaySessionRecorder.cs`, `StageEndValidation.cs`와 Unity가 생성한 `.meta`.
- Editor 수정: `TacticalCoreValidation.cs`, `RunBalanceValidation.cs`의 사례/진단 메뉴, `ChessPlaytestValidation.cs`, `PcBoardLayoutValidation.cs`의 실제 렌더 검사, `ProgressionUsabilityValidation.cs`, `MobilePlaytestValidation.cs`의 결과 보존/회귀.
- 문서: 이 감사 기록·플레이 프로토콜·워크플로우·정체성 현재 구현 표·README·검증 안내·AGENTS의 클리어 구현 상태를 맞췄다. 과거 개별 결과와 중간 실패를 현재 성공으로 덮어쓰지 않았다.

씬/Prefab/패키지/렌더 설정 변경이나 Inspector 할당은 없다. 결과 패널은 기존 Canvas·폰트·버튼을 사용하며 런타임에서 전체 Canvas를 차단하도록 배치한다. 기록 도구는 기본 꺼짐이고 제품 빌드에는 포함되지 않는다.

## 남아 있는 판단

- 화면 판독성·네 빌드의 선택 이유·반복 도주 감소는 사람 플레이 미검증.
- 실제 보스 포함 30분 검증, 고유 보스, 클리어 기록 저장, 후속 독립 스테이지·중단 복원은 미구현/미검증.
- 기존 fixture `Frame_0`에 40 PPU가 남아 있다. 새 위험 테두리의 32 PPU/Point 검사는 통과했지만 기존 아트 일괄 수정은 하지 않았다.
- 자동 런의 난이도나 봇 한 사례를 이유로 물량·피해·보상 수를 임의 조정하지 않았다.

## 재현과 설정

씬 저장 후 Play를 종료하고 `Tools > Playtest > Validate Stage One Tactical Audit` 또는 `Validate Stage One Run Smoke`를 실행한다. 통제 검사는 정상 런 상태를 덮으므로 진행 중 플레이에서 사용하지 않는다. 이번 결과는 시각별 새 파일로 보관해 과거 보고서를 덮어쓰지 않는다.

종료/복기는 `Validate Stage End and Restart`, 공통 화면은 `Validate PC Board Layout`, 보조 입력은 `Validate Mobile Touch Adapter`로 별도 검사한다. 이 메뉴들은 기존 Unity 창에서 실행한다. 실패 원본은 의도적인 재현 기록으로 보존하므로 Console/로그의 과거 실패 메시지를 현재 컴파일 실패로 해석하지 않는다.

추가 GameObject·컴포넌트·Inspector 할당·태그·레이어·Collider 설정은 없다. 새 `.meta`는 Unity가 생성했다. 저장 씬은 수정하지 않았다.
